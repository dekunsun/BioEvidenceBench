## 0. 目标和边界

**一句话**：把 BioEvidenceBench 这个评测，延伸成"可验证的环境 + 被审计过的验证器"，并用同样的纪律检查奖励函数、推理轨迹、题目难度和版本回归。

**主线不变**：BioEvidenceBench 的主线是"从历史文献到可信数据，评测每一步的可靠性"。`rl/` 讲的是下一步："把这个评测变成训练环境，并检验它的奖励函数。"

**硬规则（全部继承自 CLAUDE.md）**

1. **冻结的研究一字不动**：`FREEZE.json` 列出的文件、`PREREGISTRATION.md`、金标准文件都不改；`python src/freeze.py --verify` 每次提交前都要干净。`rl/` 只**读取** `src/score.py` 等冻结代码；要改的地方，在 `rl/` 里写副本。
2. **测试页不当训练题**：22 个样本页（6 开发 + 16 测试）和第 2 节封存的 8 页，永远不进任何训练集。
3. **旧测试集降级**：16 个测试页对 `rl/` 的所有新工作来说是**开发集**；在它们上得到的新数字，不能称为保留测试结果。
4. **标注和判断由 Gloria 做**：Claude 不写、不预填任何标签（包括学名等价标签、审题结论、奖励设计的取舍、通过标准）。Claude 可以生成候选、做统计、起草文字。
5. **只用公开数据**；模型不改写原文（任务 B 的"修复"输出只作为被评分的回答，从不写回任何源文本）。
6. **每次运行可复现**：`results/<run_id>/` 存模型名和版本、完整提示词、输入哈希、解码设置、原始输出、时间戳、花费。
7. **花钱前先试跑**：任何付费批量先跑约 5 个样本，报告单价，再按上限运行。
8. **记录位置**：`rl/` 的决定和偏离写在 `rl/LOG.md`，不写进 `DEVIATIONS.md`（那份只记原研究的偏离）。

**不进公开仓库的东西**：求职计划、故事库、案例题答案、读书笔记（私下保存）。模块一（外部基准审计）放在单独的小仓库。

## 5. 模块三：可验证环境（简版）

### 统一接口

```
reset(item_id) -> observation          # 页面文本（带行号）或一行旧 OCR，加任务说明
step(answer_json) -> reward, info      # info 里给出分项：格式是否合法、各项得分、触发的防作弊规则
```

先用纯 Python 实现，不依赖框架；包装成 Inspect 或 `verifiers` 格式作为可选的最后一步，选之前先核对两者的现状。

### 任务 A：实体抽取（只评测）

- **数据**：22 个样本页的金标准。**明确标注"不可用于训练"**。
- **奖励变体**（都用现有评分器计算，不改冻结代码）：
  - R1 严格：按提及的值级 F1；
  - R2 宽松：宽松匹配 F1；
  - R3 引语门控：引语核对失败的提及记为错误；
  - 格式错误或空回答：奖励 0，同时在 info 里单独标记。
- **奖励设计说明**（`rl/env/REWARD_DESIGN.md`，由 Gloria 拍板）：每个选择会让模型学到什么。例如：只看召回会学会撒网；只看精确会学会少答；全对才给分会让学习信号太稀疏；不罚格式错误会让模型学会用格式错误逃避扣分。
- **防作弊检查**：直接复用模块二的对抗案例，看每个奖励变体会不会被骗。

### 任务 B：OCR 逐行修复（可训练）

- **数据构建**：`src/rl_build_ocr_repair.py`：逐页下载旧 OCR；用 `score.char_map` 把旧 OCR 和专家转录按字符对齐；切成行对（旧 OCR 行 → 专家转录行）；过滤掉对齐置信度低、太短的行，以及页眉和页码。
- **题目**："把这一行 OCR 改回原书的样子，只改识别错误，不改拼写和写法。"附前后各一行作为上下文。
- **奖励**：
  - 主奖励：`1 − CER(回答, 专家行)`，截断到 [0, 1]；
  - 学名奖励：专家行里的拉丁学名候选（用 gnfinder 在专家文本上自动识别，不需要人工），回答中是否**逐字正确**；
  - **"什么都不改"基线**：直接返回原 OCR 行能得多少分，必须报告。奖励最好以"相对基线的提升"来看，否则模型可能学会"少改就是安全"。
- **防作弊检查**：原样返回、返回空、过度改写（现代化拼写、展开连字）、返回整段而不是一行。
- **污染检验（内置）**：
  - **虚构名称**：把专家行里的真实学名换成拼写合理但不存在的学名，再加上同样的 OCR 噪声（程序生成，答案已知）。比较真实名称和虚构名称的修复准确率：靠记忆的模型在虚构名称上会明显变差。
  - **反事实改动**：改地名或日期，看模型修复出来的是页面上写的，还是它记得的原值。
- **组内奖励差异（GRPO 的前提）**：GRPO 比较同一道题的一组回答，优势 = 奖励减去组内均值。一组回答奖励全一样，这道题就不产生学习信号。OCR 修复的答案几乎唯一，简单行会全对、难行会全错，所以必须测：每题采样 K 次（默认 K = 8），**组内奖励有差异的题占多少比例**。这是任务 B 能否用于 GRPO 的第一个诊断指标，写进 `REWARD_DESIGN.md`。
  - 影响这个比例的设计选择：奖励里保留连续部分（1 − CER，让"错得多"和"错得少"可区分；代价是更容易出现"少改就安全"，要和"什么都不改"基线对比）；题目粒度（一行、几行或一段；粒度越大，每次作答的决定越多）；只选含学名或明显损坏的行；采样温度。
- **试跑**：2 个模型 × 约 200 题（只用训练 / 开发书，不碰 Cuvier）。
- **产出**：`rl/env/task_a_extraction/`、`rl/env/task_b_ocr_repair/`（构建脚本、数据清单和哈希、试跑结果）、`REWARD_DESIGN.md`。
- **Gloria**：决定奖励设计；审防作弊结果。约 1 小时。
- **花费**：约 $3。

## 6. 模块五：高信号题库（简版）

- **题源**：任务 B 的训练 / 开发题（不需要标注）。
- **难度校准，分两套**（更正：难度取决于作答的模型，前沿模型觉得中等的题，小模型可能全错）：
  - **评测用**：约 300 题；Haiku、Sonnet、Gemini 各答 3 次。用于"前沿评测"的题库。
  - **训练用（为模块七准备）**：同一批题，用**目标大小的开源小模型**（0.5B–1.5B）各采样 8 次。先查 OpenRouter 上有没有合适的托管小模型（用剩余额度）；没有就推迟到 7b，在租来的 GPU 上测。
  - "通过" = 行内学名全部逐字正确，且 CER 低于事先定好的阈值（阈值写进 `rl/items/CRITERIA.md`，先写后跑）。
  - 同时报告**组内奖励有差异的题占比**（K = 8），这是训练用题库最关键的数字。
- **筛选**：两套分别保留通过率在 10%–90% 之间的题，报告各区间的题数分布，以及两套之间重合多少。如果"中间难度"的题很少，就如实写出来：这本身就是"题库是否已饱和"的证据。
- **区分度**：报告三个模型在保留题上的差距，与全部题上的差距做比较。
- **污染**：比较真实名称题和虚构名称题的通过率。
- **产出**：`rl/items/calibrated_items_frontier.csv`、`calibrated_items_small.csv`、`REPORT.md`。
- **花费**：约 $2–4（含小模型）。

## 7A. 模块七：小规模 GRPO（可选，前六个模块完成后再决定）

**目的**：能在面试中说"我在自己搭的环境上跑过 GRPO"，并亲眼看到奖励被钻空子、难度筛选是否有用。不追求训练出好模型。

### 7a 玩具版 GRPO（不花钱，用来学习和讲解）

- 约 50 行 Python，在 CPU 上用一个很小的例子跑通，**不训练真实模型**。逐步实现并可视化：
  1. 同一道题采样一组回答，算奖励；
  2. 用组内均值和标准差归一化，得到优势；
  3. 新旧策略的概率比乘以优势，再截断（clip），和 PPO 相同；
  4. 可选：对参考模型的 KL 惩罚；
  5. token 级损失的汇总方式。
- 配一份讲解笔记，回答常见追问：组内奖励全一样会怎样；采样数、温度、KL 系数怎么影响训练；奖励尺度的影响；按 token 平均是否会偏向长回答或短回答（有论文分析过 GRPO 的长度归一化偏差，如 Dr. GRPO；引用前核实）；动态过滤全对或全错的组（如 DAPO；引用前核实）。
- **产出**：`rl/grpo/toy_grpo.py`、`rl/grpo/NOTES_zh.md`。

### 7b TRL 实验（需要 GPU）

- **工具**：Hugging Face TRL 的 `GRPOTrainer`，接自定义奖励函数（任务 B 的奖励）。**不自己实现优化器**：面试考的是环境、奖励、数据和评测，而且自写优化器出错很难发现。TRL 更新快，开工前先读当前文档，并把版本锁进依赖。
- **模型**：0.5B–1.5B 的开源模型，可能需要 LoRA；生成环节可能需要 vLLM。
- **对照实验**：两组训练数据，其余设置完全相同：
  1. 从训练 / 开发书**随机抽**的题；
  2. **模块五筛过**的题（按小模型校准）。
- **每次运行记录**：TRL、模型和依赖的版本，全部超参数，随机种子，奖励曲线，**每一步组内奖励有差异的比例**，学名逐字正确率，"什么都不改"基线。
- **评估**：训练前后在 **Cuvier 留出书**上比较（跨书、跨语言）；检查模型有没有学会作弊（原样返回、过度改写、只改简单字符）。
- **小模型太弱的应对**：如果几乎全错（组内没有差异），先用少量监督微调把模型"带上路"，或者换成更简单的子集，并如实记录。
- **硬件**：这个云环境没有 GPU，需要 Gloria 的账号租用（如 Hugging Face Jobs、Colab、RunPod）。**开始前先核实价格**；粗估几十美元，另加一两天调试。
- **产出**：`rl/grpo/trl_experiment/`（配置、日志、曲线）、`REPORT.md`（一页：随机题与筛过的题对比，作弊观察，结论和局限）。

### 7c 改进归因：模型究竟从哪里变好

奖励上升不算数。7b 的报告按下面四个问题依次回答，每一项都写清用了什么数据、什么方法。

**1. 真的变好了吗？**
- 用**不参与训练的指标**判断：Cuvier 留出书上的 CER、学名逐字正确率，加上人工抽检约 50 行（Gloria 抽检，记录用时）。
- 对照：训练前的模型；"什么都不改"基线。
- 至少 2–3 个随机种子；置信区间按页重抽样。

**2. 在哪些地方变好？**
- **按错误类型**：把错误按字符类型分类（学名里的字母、普通单词、连字、长 s、数字、标点、断词），分别比较训练前后。
- **按改动行为**：改动率（改了多少处）、改动精确率（改的里面多少改对）、改动召回率（该改的里面改了多少）。区分"改得更多"和"改得更准"。
- **按训练前难度**：原本 0%、10%–90%、100% 通过的三组题各自的提升；按 GRPO 的原理，提升应集中在中间组。

**3. 为什么变好？**
- **数据选择**：随机题与筛过的题两次训练的对比（7b 已安排）。
- **学会了，还是"磨尖"了**：比较训练前的 pass@k（采样 k 次至少一次对）和训练后的 pass@1。如果训练后的 pass@1 只是逼近训练前的 pass@k，说明 RL 主要是让模型更稳定地给出它本来就能给出的答案，而不是学会了新东西（相关讨论见 Yue 等 2025 关于 RLVR 是否扩展推理能力的研究；引用前核实）。
- **读出来的，还是记住的**：真实学名与虚构学名的提升幅度对比。
- **能否迁移**：训练书与 Cuvier 留出书（跨书、跨语言）的提升对比。
- **直接读例子**：挑出训练前错、训练后对的行，以及训练后反而变错的行，逐行读，用模块四的失败类型表归类。

**4. 付出了什么代价？**
- **副作用**：任务 A（实体抽取）等其他任务上有没有变差。
- **训练过程**：奖励曲线、组内奖励有差异的比例、输出长度、与参考模型的 KL，随训练步数的变化；标出"奖励涨、留出指标不涨"或"输出变怪"的时刻。

**产出**：`rl/grpo/trl_experiment/ATTRIBUTION.md`，每个问题一节，每节有数字、区间和例子。
